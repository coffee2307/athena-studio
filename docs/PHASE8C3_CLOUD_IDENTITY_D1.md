# Phase 8C.3 — Cloud-ready independent Athena Identity (no deployment)

## What is real and tested

- An independent Cloudflare Worker under `workers/identity/src/` with Better Auth v1.7.12, Drizzle ORM and a Cloudflare D1 database binding. There is **no Supabase Auth SDK** in the Worker or its database schema.
- Seven D1/SQLite tables: Better Auth `user`, `account`, `session`, `verification`, `rateLimit`, plus Athena `athena_workspace` and `athena_membership`. Schema SQL is generated by Drizzle Kit and tracked in `workers/identity/migrations/`.
- Login architecture: Google OAuth or GitHub OAuth for identity only; optional six-digit email OTP with five-minute validity, three allowed guesses, hashed OTP at rest, signed sessions and persistent D1-backed request rate limits. Actual Google/GitHub/Gmail credentials are **not** configured and **no real provider login/mail has occurred**.
- Portable Gmail API transfer code was extracted to `lib/identity/gmail-core.ts` and reused by local and Cloudflare adapters; it sends via `gmail.send` only when credentials are present. No automatic retries after an uncertain acceptance.
- Read-only `GET /api/workspaces` requires a verified Better Auth session and lists **only the user's own memberships**. Both A/B cross-tenant scenarios were tested in emulated D1 with actual Better Auth sessions, cookies and deliberate revocation of A's email verification.
- Schema enforces FK constraints, workspace kinds, valid membership roles, and a unique membership per user/workspace. No API for admin grants, customer repositories, arbitrary SQL or documents is exposed.
- Default tracked Wrangler config: `workers_dev=false`, blank expected origin, feature flag `ATHENA_CLOUD_IDENTITY_ENABLED=false`, D1 database ID all zeros (placeholder) and no routes or secrets. Production website and legacy staging stay unchanged.
- Offline tests: signed OTP issues; bad OTP fails; OTP replay fails; stores a hash; actual session read from D1; no cross-tenant workspace reads; forged cookies/revoked email verification denied; cross-origin/oversize POST rejected. Wrangler local D1 migration succeeded and `wrangler deploy --dry-run` produces a bundle without deploying.
- Enabled **local-only Workerd** smoke (ignored `.qa` config and randomized local secret; fake OAuth IDs, no real provider): `GET /healthz` 200 configured-only, `GET /api/identity/get-session` 200 null, anonymous `GET /api/workspaces` 401, cross-origin POST 403. No internet OAuth sign-in or mail was attempted.
- The one-time Drizzle Kit schema generator was removed from repository dependencies after committing the generated SQL, because its transitive old esbuild packages showed four moderate npm advisories. Future schema regeneration requires separately reviewed/patched tooling; never change the schema without producing and auditing a migration.

## Architecture

Visitor -> Athena frontend -> **future same-origin routing** -> Cloudflare Identity Worker -> D1.
Google/GitHub = optional identity attestations, Gmail API = optional OTP transport. Athena independently defines accounts, sessions, membership policy and UX.

### Critical integration restriction

Do **not** point the current Client Portal directly at a different `workers.dev` hostname and assume session cookies will work. Before launch, choose an owner-controlled same-site HTTPS hostname/route and verify cookie `Secure`/`HttpOnly`/`SameSite`, CSRF, callback URLs, sign-out, recovery, redirects, cross-domain protections, session invalidation and provider account linking. The existing Client Portal remains protected under its legacy gates and is NOT migrated by this change.

### Fail-closed design

- OFF by default and returns HTTP 503 for all identity/workspace endpoints.
- Rejects if enabled with a mismatched request origin, missing database, weak/missing secret, absent identity provider, invalid Google/GitHub credential pair, or incomplete Gmail credentials.
- Production requires HTTPS; local `http://localhost` or `http://127.0.0.1` is allowed **only** with explicit local override.
- No browser-visible database binding or refresh token. Worker POSTs require matching `Origin`, JSON, and a 16 KiB maximum body; no wildcard CORS.
- Better Auth checks provider-verified emails for accounts; no implicit linking between GitHub, Google and existing email accounts.
- DB-layer membership integrity constraints plus API userId scoping. D1/SQLite does not offer PostgreSQL RLS — sensitive endpoints need individual authorization tests before addition.
- Built-in server-side limits use D1 `rateLimit`. On the Cloudflare edge use the overwritten `cf-connecting-ip` header, not an attacker-controlled X-Forwarded-For chain.

## Local development — ZERO cloud or paid-provider resources

Run from the Athena repository:

```powershell
npm ci
npm run identity:d1:local:migrate
npm run identity:d1:local:dev
```

The Worker starts with **Auth disabled**. Local `GET /healthz` reports only configuration status. `GET /api/identity/get-session` and `GET /api/workspaces` return HTTP 503. Files created by Wrangler remain gitignored under `.qa/` or `.wrangler/`. Commands above never use `--remote` or `wrangler deploy`.

For repeatable offline D1 Auth + A/B tests:
```powershell
node --test tests/phase8c3-cloud-identity.test.mjs
```

The tests use Wrangler `getPlatformProxy({remoteBindings:false,persist:false})`, create a fresh **ephemeral** D1 database with migration SQL, and inject an in-memory OTP recipient. They do not contact Google, GitHub, Gmail, Supabase or Cloudflare's remote D1 service.

For build validation:
```powershell
npx wrangler deploy --dry-run --config workers/identity/wrangler.toml --outdir .qa/worker-dryrun
```
This is a dry run only; the tracked config cannot provide live credentials/routes.

## Provider setup checklist before any live tests

1. Owner chooses an approved Cloudflare Free workspace and creates **an isolated D1 staging database**, verifies quota/billing settings, and explicitly approves activation. No resources have been created by this branch.
2. Owner approves a single HTTPS origin for the auth Worker and exact OAuth callback URLs `https://<approved-origin>/api/identity/callback/google` and `.../callback/github`. Never register arbitrary callback domains.
3. Google Cloud OAuth client for login; GitHub OAuth client for login. Configure minimal identity scopes, verified email and provider review. Credentials remain server-side. GitHub OAuth **does not grant repo contents permission**.
4. To manage client repositories, create a **separate GitHub App installation consent**: customer chooses repositories, Athena requests minimal read-only access first, and grants/revocation must be audited. No repo management was enabled in this phase.
5. For email OTP, approve the Gmail account and OAuth `gmail.send` scope, provide sender and refresh credential in Worker secrets, confirm transactional deliverability, spam rules, quotas and abuse prevention. Gmail still has its own provider limits. If unavailable, do not expose fake OTP.
6. Apply only reviewed migrations on isolated cloud D1, test backups/restores and zero-data-loss recovery, A/B tenant isolation, user account recovery, admin provisioning, performance under concurrent load, OAuth CSRF/state and signed session protections, IP rate limits, free Worker CPU (10 ms/request), quota alerts and outage UX.
7. Only after all gates pass, migrate identities using explicit account linking/re-verification. **Never copy existing Supabase user UUIDs or grant Admin from matching emails without authorization and verification.**
